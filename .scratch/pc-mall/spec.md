# 电脑智能选配与商城联动系统实施规格

Status: ready-for-agent

版本：1.0

发布日期：2026-10-28

本规格由已确认的需求基线、实施决策及 GitHub 复用建议综合形成。发布状态表示规格可用于后续任务拆分，不表示业务已经实现、环境已验证或测试已通过。

## Problem Statement

用户需要将硬件商品浏览、DIY 装机、兼容性检测、预算推荐与商城购买连接起来。配置必须引用商城真实商品，价格、库存和参数发生变化后需要重新校验，订单必须保留成交时的历史信息。

当前仓库只有协作配置，没有业务实现、数据库迁移或自动化测试。本规格将已批准需求、已确认实施决策及 GitHub 复用建议整合为开发依据。

需求基线为《电脑智能选配与商城联动系统_软件需求分析报告.docx》，需求和验收编号沿用《需求追踪矩阵.xlsx》。本次来源文件指纹见 Further Notes。

本规格承接全部七模块 P0、公共商品浏览能力及适用的业务规则和非功能要求。不得通过实现简化改变冻结需求；发生实质冲突时应指出原编号并走变更确认。

## Solution

建设一个供电脑浏览器使用的自营硬件商城：

- 游客可以浏览商品、编辑 DIY 配置、执行兼容检测和获取预算推荐。
- 登录用户可以管理个人资料，将单品或完整配置组加入购物车，混合结算、模拟支付并查看本人订单。
- 管理员通过统一登录入口维护商品、参数、评分、价格、库存及普通用户状态，并完成已支付订单。
- 后端统一负责认证、规则、价格、库存和订单状态；前端提供交互及诊断展示。
- 首次交付在本机完整运行，并提供可复现的数据库初始化、构建、启动和演示说明。

## User Stories

以下用户故事用于组织交付行为，不替代原需求、规则及验收编号。

### 公共商品能力

1. 作为游客，我希望按类别浏览和搜索硬件商品，以便找到候选配件。
2. 作为用户，我希望查看商品名称、品牌、型号、售价、库存和技术参数，以便理解选择依据。
3. 作为游客，我希望无需登录即可浏览、DIY、检测和推荐，以便先体验平台。

### F01 用户与权限

4. 作为游客，我希望通过用户名和密码注册普通账户，以便获得购买权限。
5. 作为账户持有人，我希望通过统一入口登录，以便使用本人及对应角色的功能。
6. 作为登录用户，我希望退出后当前会话立即失效，以便结束本次访问。
7. 作为用户，我希望登录过期时收到明确提示，以便重新认证后继续操作。
8. 作为普通用户，我希望后台权限由服务端检查，以便其他用户不能绕过界面修改管理数据。
9. 作为登录用户，我希望查看本人基本资料，以便确认账户信息。
10. 作为登录用户，我希望修改本人昵称，以便更新显示名称。
11. 作为登录用户，我希望验证旧密码后修改密码，并使相关旧会话失效，以便保护账户。
12. 作为管理员，我希望禁用账户后其登录和受保护请求被拒绝，以便账户状态真正生效。
13. 作为游客，我希望登录后恢复当前标签页配置并重新校验，以便继续装机而不自动加购。
14. 作为用户，我希望错误凭证、异常输入和登录限流有明确反馈，以便知道操作结果。
15. 作为用户，我希望个人资料、购物车和订单按本人隔离，以便其他用户不能越权访问。

### F02 DIY 装机

16. 作为用户，我希望在三栏工作区查看八类硬件、候选商品和当前配置，以便逐步选配。
17. 作为用户，我希望按任意顺序选择真实商品，以便按自己的思路装机。
18. 作为用户，我希望同类别重新选择时替换原商品，以便调整配置而不形成重复类别。
19. 作为用户，我希望移除已选配件并更新总价、完整性和检测结果，以便继续修改。
20. 作为用户，我希望清空配置前确认，以便避免误删当前工作区。
21. 作为用户，我希望配置参考总价随有效商品价格更新，以便了解当前成本。
22. 作为用户，我希望看到七类基础硬件与条件必需独显的缺失情况，以便补齐配置。
23. 作为用户，我希望配置变化后自动检测，也能手动重检，以便获得当前结论。
24. 作为用户，我希望看到具体问题且旧请求不能覆盖新配置结果，以便正确调整配件。
25. 作为用户，我希望刷新当前标签页时尽可能保留配置，以便继续本次编辑。
26. 作为登录用户，我希望主动确认后将合法配置交给购物车，以便购买实际配件。

### F03 硬件兼容检测

27. 作为用户，我希望检测使用服务端当前商品参数，以便结论不受客户端伪造数据影响。
28. 作为用户，我希望未选齐硬件时也能检查已有条件，以便尽早发现问题。
29. 作为用户，我希望执行全部适用的十项核心规则，以便核对明确支持的兼容关系。
30. 作为用户，我希望区分通过、失败、未知、缺件和不适用，以便理解检测依据。
31. 作为用户，我希望综合状态同时保留缺件清单和冲突明细，以便已有问题不会被单一摘要隐藏。
32. 作为用户，我希望结果包含规则版本、配置修订和检测时间，以便识别过期结果。
33. 作为用户，我希望参数或配置变化后旧结论失效，以便重新验证当前方案。
34. 作为用户，我希望检测异常时保留编辑内容并明确报错，以便不会把旧成功结果误认为本次通过。
35. 作为购买者，我希望 DIY、推荐、加购和下单复用同一套核心规则，以便获得一致的整机准入结果。

### F04 智能推荐

36. 作为用户，我希望输入有效预算并选择办公、游戏或内容创作，以便获得对应建议。
37. 作为用户，我希望推荐应用对应用途的最低配置和独显要求，以便结果符合内部场景策略。
38. 作为用户，我希望推荐只使用有效商品及必要参数，以便结果能够进入商城购买流程。
39. 作为用户，我希望 CPU/GPU 评分有来源和固定版本，以便结果可以解释和复现。
40. 作为用户，我希望系统按既定权重在预算内搜索配置，以便进行性能与成本取舍。
41. 作为用户，我希望相同数据下推荐排序稳定，以便重复请求获得可复现结果。
42. 作为用户，我希望查看商品明细、总价、预算余额、评分、兼容结果和基础理由，以便理解推荐。
43. 作为用户，我希望缺货、数据不足、预算不足、无兼容组合和搜索未找到结果被正确区分，以便决定如何调整。
44. 作为用户，我希望推荐方案能无损进入 DIY 编辑，以便按需要修改，并明确旧评分和解释何时失效。
45. 作为用户，我希望推荐加购遵守登录、用户确认和当前数据重验，以便不会沿用失效结果交易。
46. 作为用户，我希望生成推荐本身不锁价或预占库存，以便推荐与交易阶段的含义清晰。

### F05 购物车

47. 作为登录用户，我希望购物车持久保存并仅本人可访问，以便重新登录后继续购买。
48. 作为登录用户，我希望普通单品重复添加时合并同 SKU 数量，以便避免重复记录。
49. 作为登录用户，我希望修改普通单品数量时检查 1～99 和当前库存限制，以便保持数量合法。
50. 作为登录用户，我希望删除单品时不影响配置组，以便独立管理购物项。
51. 作为登录用户，我希望整套配置在结构、商品和兼容性复核成功后原子入车，以便不会留下部分配置。
52. 作为登录用户，我希望配置组清楚展示组内真实 SKU，且不能在车内拆改配件数量，以便保持一套电脑的完整含义。
53. 作为登录用户，我希望返回 DIY 编辑后整组替换，失败或取消时保留旧组，以便安全修改。
54. 作为登录用户，我希望完全相同的配置重复添加时被识别，以便避免意外重复分组。
55. 作为登录用户，我希望单品和不同配置组可以引用同 SKU，并汇总库存需求，以便混合购买时正确核算。
56. 作为登录用户，我希望金额由服务端计算，价格变化时先确认，以便了解当前结算金额。
57. 作为登录用户，我希望失效项保留并标明原因，以便调整选择而不丢失记录。
58. 作为登录用户，我希望选择部分购物项结算，配置组只能整体选择，以便控制本次购买范围。
59. 作为登录用户，我希望结算交接、重复请求和并发编辑有安全检查，以便不会丢数量或破坏分组。

### F06 订单与模拟购买

60. 作为登录用户，我希望只能从本人服务端购物车的有效选中项下单，以便拒绝伪造明细和过期购物车内容。
61. 作为登录用户，我希望一笔订单支持单品和多个完整配置组，并保留归属，以便混合购买。
62. 作为登录用户，我希望下单重新检查商品、库存和整机规则，普通单品不受整机完整性限制，以便按正确规则购买。
63. 作为登录用户，我希望确认后的价格再次变化时仍需重新确认，以便不会静默成交。
64. 作为登录用户，我希望订单、库存预占、成交快照和购物车清理整体成功，以便交易状态一致。
65. 作为登录用户，我希望任一步骤失败时整体回滚，以便不出现半成品订单或错误库存。
66. 作为登录用户，我希望成功下单只清理本次选中项，以便保留其他购物选择。
67. 作为购买者，我希望订单保存成交快照，以便后续商品变更不会改写购买历史。
68. 作为订单所有者，我希望在支付期限内模拟支付，且不再次扣减库存，以便完成站内支付流程。
69. 作为订单所有者，我希望取消待支付订单并只释放一次库存，以便安全终止购买。
70. 作为用户，我希望超时订单自动取消，扫描延迟也不能放行过期支付，以便截止时间可靠。
71. 作为用户，我希望重复下单、支付、取消及并发操作不重复产生副作用，以便请求重试安全。
72. 作为管理员，我希望只能通过受控服务完成已支付订单，以便避免非法状态跳转。
73. 作为登录用户，我希望查看本人订单列表和成交明细，以便了解购买结果。

### F07 后台管理

74. 作为管理员，我希望统一登录后进入有导航和操作反馈的后台，以便维护商城。
75. 作为管理员，我希望分页查询商品并查看完整详情，以便定位需要维护的记录。
76. 作为管理员，我希望新增商品默认下架，且 SKU 和类别创建后不可修改，以便保持商品身份稳定。
77. 作为管理员，我希望维护基础信息、图片地址和分类专属参数，以便提供有效商品数据。
78. 作为管理员，我希望上架校验必要字段，下架时保留历史关联，以便控制新交易而不破坏历史。
79. 作为管理员，我希望受控修改价格和库存并记录调整原因，以便与交易库存协同。
80. 作为管理员，我希望维护有来源和版本的评分数据，但不能停用核心检查或任意改变冻结策略，以便保持推荐和检测可信。
81. 作为管理员，我希望查询普通用户并启用或禁用其账户，同时保护管理员及角色字段，以便安全管理账户。
82. 作为管理员，我希望按订单号、状态和用户等基本条件查询订单及成交分组，以便核对业务结果。
83. 作为管理员，我希望关键变更留下原子提交的审计记录，且后续业务使用新数据，以便追溯操作。

### 交付与质量

84. 作为使用者，我希望在本机按说明完成初始化、启动和演示，以便复现完整平台。
85. 作为使用者，我希望输入错误、失效商品、状态冲突和服务异常有清楚反馈，以便继续操作。
86. 作为开发者，我希望规则、事务和完整路径具备可复现测试，并关联原验收编号，以便验证实现符合基线。

## Implementation Decisions

### 应用结构与公共契约

- 采用单仓库、模块化单体。公共商品能力与 F01～F07 按业务职责组织；后台复用对应领域服务，不建立平行认证、兼容规则或订单状态逻辑。
- 后端采用 Spring Boot、Spring Security、MyBatis 和 MySQL；使用版本化 SQL 迁移。前端采用 Vue 3、Vite、TypeScript 和 Element Plus。
- 开发时前端代理后端接口；演示时由后端提供构建后的页面，保持同源。依赖选择兼容的正式发布版本并锁定，不能照搬参考项目的旧版本。
- 接口使用结构化 JSON，明确区分业务成功、校验失败、未认证、无权限、价格变化、并发冲突和系统异常。未认证及角色权限不足沿用 401、403。
- 身份取自认证 Session，商品价格、库存和兼容结论取自服务端。客户端提交的所属用户、成交价格和“检测通过”字段不能作为可信依据。
- 金额统一为 CNY、两位小数和精确十进制运算。前端展示金额不能成为结算依据。

### F01 认证与账户

- 普通用户与管理员共用用户名密码入口；正式角色仅 USER、ADMIN，游客是未登录状态。
- 用户名为 4～20 位英文字母、数字或下划线，大小写不敏感且唯一；昵称最长 30 字符。
- 密码遵守基线的 8～64 字符及 UTF-8 不超过 72 字节限制，使用 BCrypt；注册成功后进入登录，不自动建立会话。
- Session 无操作两小时失效；退出使当前会话失效，改密使相关旧会话失效，禁用账户不能继续使用受保护能力。
- 修改状态的浏览器请求启用 CSRF 防护。Cookie 的 HttpOnly、Secure、SameSite 按本机演示与部署环境正确配置。
- 登录失败采用可配置限流；报告中的示例阈值不升级为不可变业务要求。
- 管理员通过初始化建立，凭据不明文提交；不开放管理员注册、普通用户角色提升或任意改密入口。

### 商品、参数与配置

- 商城仅销售 CPU、主板、独显、内存、SSD、电源、机箱、独立散热器八类硬件。
- 商品基础数据与分类专属参数分开组织；多值参数使用集合语义。SKU、商品 ID 唯一，SKU 和类别创建后不可修改。
- 装机配置是实际商品的逻辑组合，每类最多一个 SKU、一个销售单位；不产生整机 SKU 或整机独立库存。
- CPU、主板、内存、SSD、电源、机箱和独立散热器为基础必需；独显按有效图形输出路径条件必需。
- 内存套装按总标称容量和实际条数分别记录。SSD 使用十进制 GB，1 TB＝1000 GB；原始数值与单位保留，GiB/TiB 显式换算。功率统一 W，尺寸统一 mm。
- 临时 DIY 配置在当前标签页使用 sessionStorage 保存商品引用、来源和修订信息；P0 不建立永久游客账户或多方案库。
- 配置变化后更新参考报价及检测。异步结果必须匹配当前配置修订，旧响应不得覆盖新状态。

### F03 统一兼容规则

服务端实现并复用以下十项核心检查：

| 编号 | 检查 |
| --- | --- |
| C01 | CPU 与主板插槽 |
| C02 | 内存代际与实际条数 |
| C03 | CPU 与独立散热器插槽 |
| C04 | 主板板型与机箱支持集合 |
| C05 | SSD 物理规格、接口及协议 |
| C06 | 独显与主板安装接口 |
| C07 | 经确认有效的核显或独显输出路径 |
| C08 | 电源额定功率与冻结估算模型 |
| C09 | 显卡长度与机箱有效限制 |
| C10 | 散热器高度与机箱有效限制 |

- C08 最低需求为 `ceil(1.30 ×（CPU 峰值功耗估算＋GPU 总板功耗估算＋80W）)`；无独显时 GPU 项为零，不机械以 CPU TDP 替代峰值估算。
- 分项状态保留 PASS、FAIL、UNKNOWN、PENDING、NOT_APPLICABLE。
- 综合状态保留 CORE_PASSED、INCOMPATIBLE、INCOMPLETE、UNVERIFIED、ERROR。正常检测时明确冲突优先于缺件，缺件优先于未知，同时保留所有诊断；异常返回 ERROR。
- 只有必要配件完整且全部适用 P0 检查实际通过，才能令 corePassed 为 true。它不代表商品可售、有库存、用户有权限或现实全部兼容。
- 结果包含规则编号、关联类别、解释、缺件清单、配置修订、规则版本和时间。未执行的扩展检查如实说明，不能伪装为通过。

### F04 推荐与评分

推荐门槛和权重直接继承基线：

| 用途 | CPU 下限 | GPU 下限 | RAM | SSD | 独显 | CPU/GPU/RAM/SSD 权重 |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| 办公 | 25 | 不适用 | 8 GB | 256 GB | 可选，有效核显路径可替代 | 50%/0%/30%/20% |
| 游戏 | 35 | 40 | 16 GB | 512 GB | 必需 | 30%/55%/10%/5% |
| 内容创作 | 35 | 35 | 16 GB | 512 GB | 必需 | 35%/35%/20%/10% |

- CPU/GPU 使用已确认的 Blender Open Data 固定版本渲染参考。原始数据、准确型号、采集与快照信息、样本条件和转换版本需可追溯；不混用未经区分的版本或测试条件。
- CPU 原始参考点 0、50、200、450、800，对应内部 0、25、50、75、100；GPU 原始参考点为 0、500、2000、4500、8000。相邻点线性插值，最高封顶 100。
- 上述映射属于已确认的项目内部策略，不是 Blender 发布的硬件等级，也不代表游戏 FPS 或通用性能。
- RAM：8/16/32 GB 对应 50/80/100；SSD：256/512/1000 GB 对应 40/75/100。按基线插值、低端按比例、达到满分后封顶。
- 推荐执行候选筛选、场景门槛过滤、增量约束剪枝、有界 Beam Search、F03 完整复核和稳定排序。
- 初始单类别候选上限 15、束宽 64，P0 返回一套；兼顾低成本和高性能候选。
- 有效候选最高分为 U_max，在不低于 U_max－1 的候选中优先选最低价，同价按固定商品 ID 顺序决定。
- 成功结果必须同时满足预算、场景门槛、配置完整性、核心检查、可售性、库存及数据有效性。
- 保留 SUCCESS、INVALID_INPUT、NO_AVAILABLE_PRODUCT、INSUFFICIENT_DATA、BUDGET_INSUFFICIENT、NO_COMPATIBLE_COMBINATION、NO_RESULT_FOUND、REVALIDATION_REQUIRED、SYSTEM_ERROR 的既有语义。
- 启发式搜索未找到不能推导全局无解；预算不足和最低价声明必须有可靠依据。
- 推荐进入 DIY 后，修改使旧评分和解释失效；下游不继续强制旧预算。推荐不锁价、不预占库存。

### F05 购物车与报价确认

- 每名用户一个持久化逻辑购物车，包含普通单品和配置组。单品同 SKU 合并，数量为 1～99；配置组保持独立身份。
- 配置去重基于规范化类别、SKU 和数量，不依赖名称、来源或价格。
- 配置添加、替换和删除保持整体一致；编辑经 DIY 完成并复验，失败或取消保留旧组。
- 加购及增加数量时汇总购物车同 SKU 需求；结算时按本次选中项汇总。普通单品 99 件上限不机械套用于跨项聚合总量。
- 购物车读取现价、计算金额并保留失效项；未选中的无效项不阻断其他有效选择。
- 用户确认报价后，创建订单仍复核服务端当前价格和购物车内容。报价确认不能变成锁价，二次变价必须再次确认。
- 配置组只能整体选择和结算。结算预检查不创建订单或预占库存。

### F06 订单、库存与幂等

- 使用 MySQL 事务、固定顺序行锁、唯一约束和持久化幂等记录，不额外引入 Redis 或消息队列。
- 对购物车并发修改、商品变更和库存更新建立统一的一致性边界；管理写入遵守同一锁定与事务规则。
- 幂等标识与用户、操作和请求内容绑定。同标识同内容重试返回已处理结果，同标识不同内容拒绝。
- 创建订单重新核验服务端选中项、当前商品和价格、同 SKU 总量及每套配置的 F03 结果。
- 订单、库存预占、成交快照、选中购物项清理在一个事务内提交或回滚。
- 创建成功进入 PENDING_PAYMENT，支付截止为创建后 30 分钟。
- 合法状态转换仅为：待支付到 PAID 或 CANCELLED；PAID 经管理员完成到 COMPLETED。取消和完成为终态，已支付不支持待支付取消或退款。
- 支付使用服务端时间，必须早于截止时刻；达到截止时刻即拒绝，不依赖扫描是否运行。
- 每分钟扫描过期订单。取消及超时只释放一次预占，不自动恢复购物车；失败处理可以安全重试。
- 支付及完成不再次扣减可售库存。支付、取消、超时和完成竞争时，最多产生一次合法转换及相应副作用。
- 快照保存成交 SKU、名称、型号、类别、单价、数量、小计和配置归属，后续商品修改不能覆盖。

### F07 维护与审计

- 商品默认 OFF_SALE，满足必要信息和适用参数要求后才允许 ON_SALE；不物理删除商品或历史业务数据。
- 库存通过受控业务服务调整，不能覆盖预占关系；记录原因、操作者及前后值。
- 评分维护必须保留来源与版本，不能以缺失值冒充有效评分；P0 不提供任意修改场景公式和权重的后台功能。
- 仅能管理普通 USER 的启用和禁用，不允许提升角色或修改受保护管理员信息。
- 后台提供基本商品、用户和订单查询。订单完成复用 F06，不能任意修改状态、金额或快照。
- 上下架、价格、库存、关键参数、账户状态及订单完成等关键操作记录审计；需要原子审计的操作与业务变更一致提交。
- P0 要求审计记录可核验，不将专用审计筛选页面升级为必做项。

## Testing Decisions

### 已确认的测试边界

以应用公开的后端业务接口和浏览器可观察行为作为主要测试边界，使用真实独立 MySQL 测试库验证持久化结果；F03/F04 的确定性规则入口用于快速、精确的边界测试。该测试边界已在实施准备阶段与用户确认。

- 规则单元测试覆盖 F03、F04 的输入与结果。
- 集成测试覆盖认证、购物车、订单、库存和审计，重点验证事务及并发结果。
- 浏览器测试覆盖核心用户路径、状态反馈、配置恢复和前后端契约。
- 测试库与演示库隔离，测试清理只能作用于明确配置的专用测试库。
- 当前仓库没有既有测试先例。参考项目源码不等于本平台已经具备测试证据；框架接入参考官方示例，验收断言依据本项目基线建立。

### 必须覆盖的场景

- F01：注册、重复用户名、密码限制、统一登录、退出、过期、禁用、改密失效、401/403、CSRF 和越权。
- F02/F03：任意选配顺序、七类完整性、核显路径、十项规则、尺寸与功率边界、未知参数、缺件与冲突并存、旧响应晚到和检测异常。
- F04：三用途门槛及权重、固定评分映射和容量节点、预算边界、候选失效、数据不足、稳定排序、低价兜底及无解声明的证据边界。
- F05：单品合并、数量边界、配置去重、整组写入失败、修改失败保留旧组、失效项保留、整体选择和库存聚合。
- F06：事务故障回滚、有限库存并发购买、报价二次变化、购物车并发修改、重复请求、相同幂等键不同内容、支付截止恰好到达、取消与超时竞争、重复完成和历史快照稳定。
- F07：上架校验、保护字段、参数与评分变更生效、后台与下单并发、普通用户禁用、订单受控完成及原子审计。

并发和时间测试应使用可协调的并发启动及可控制时钟，验证外部结果，不依赖随机等待或内部调用次数。

### 完整路径与性能

至少验证：

1. 游客浏览与搜索商品。
2. 游客 DIY，登录恢复、重验并主动加购。
3. 三场景推荐，转入 DIY，再进入配置组交易。
4. 单品与多个配置组混合结算、模拟支付、管理员完成。
5. 订单取消和超时释放库存，后续商品变更不改成交快照。

性能验收沿用报告条件：

| 能力 | 目标及条件 |
| --- | --- |
| F03 | 完整配置检测 P95≤1 秒；约 100～200 商品、四核 8GB 级环境、预热后 10 并发 |
| F04 | 推荐 P95≤3 秒；约 100～200 完整商品、10 并发 |
| F05 | 普通操作 P95≤2 秒；保留约 100 商品、20 并发、≤30 明细的暂定测试口径 |
| F06 | 查询 P95≤2 秒，下单 P95≤3 秒；固定单机、至少 100 商品、20 并发 |
| F07 | 保留分页查询优先争取 2 秒内的初步目标，不升级为独立硬指标 |

记录实际软硬件、数据、预热、并发及统计口径。30 条明细是测试条件，不自动变成产品数量限制。

验收追踪中的既有场景保持原编号；本版执行适用 P0，P1/P2 明确标注未纳入。补充测试使用独立标识，不伪造原冻结编号，也不把“需求已确认”记作“测试已通过”。
